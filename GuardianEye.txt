Merged Project Proposal
GuardianEye: Unified On-Device Multimodal Child Safety App
Combining the on-device visual protection engine (GuardianEye / SafeScreen AI) with an on-device adaptation of the text-based bullying/harassment detection concept (Cyber Care)
1. Why Merge These Two Ideas
GuardianEye (and its SafeScreen AI pitch) protects children from one class of harm — explicit visual content — using a fast, fully on-device pipeline with no server upload. Cyber Care protects against a different class of harm — bullying, harassment, and unsafe social interactions — but does so through cloud-based text analysis of linked social media accounts.
These two systems do not overlap in what they detect (visual vs. textual threats), so combining them does not duplicate effort — it produces a more complete child-safety product. The main architectural change needed is bringing Cyber Care's detection concept on-device, so the merged system keeps a single, consistent privacy story: nothing — neither images nor text — ever leaves the device.

4. Where the Novelty Comes From
●	Multimodal coverage: most existing parental-control tools handle either images (NSFW filters) or text (bullying detection) — rarely both in one on-device pipeline.
●	Fully on-device for both modalities: Cyber Care's text analysis currently depends on cloud APIs; moving it on-device (matching GuardianEye's existing no-upload architecture) is the core technical contribution.
●	Shared capture pipeline: the same screen-capture stream (MediaProjection) can feed both the image classifier (M2) and, after OCR, the text classifier (M3) — this reuse is an efficient systems-design angle worth highlighting in the report.
●	Single consistent privacy claim across both threat types, which is stronger (and easier to defend to evaluators) than two separate, inconsistent architectures.
5. Suggested Scope Cuts (to keep the FYP realistic)
The full Cyber Care feature set (social-media account integration, friend-list personality analysis, sentiment/mood dashboards) is too large to fully re-architect on-device within an FYP timeline. Recommended MVP scope:
●	Keep: on-device text classification for bullying/harassment on text extracted from the screen (via OCR) or from a narrow explicitly-granted input source.
●	Cut from MVP, list as Future Work: social-media account linking, friend-list analyzer, personality-trait prediction, sentiment/mood visualization dashboards.
●	This keeps the SRS's existing ethical/legal boundaries intact (Section 8 of the GuardianEye SRS already excludes message/SMS content scanning for privacy/legal reasons — scope M3 carefully around this: analyze only what is visibly rendered on-screen, not private message contents, to stay consistent with that boundary).
6. Suggested Staged Roadmap
Stage	Deliverable
0	Environment setup: Android Studio, test devices, repo, model sourcing (NSFW model + lightweight text-classification model).
1	Standalone validation of both models offline (NSFW classifier on sample images; text classifier on sample bullying datasets).
2	Screen capture pipeline (MediaProjection) implemented — no ML yet.
3	M2 wired in: NSFW classifier + blur overlay working end-to-end (MVP checkpoint 1).
4	OCR/text-extraction pipeline added on top of the same capture stream.
5	M3 wired in: on-device text classifier flags bullying/harassment text (MVP checkpoint 2 — novelty milestone).
6	M1: Device pairing + Device Owner lock-down.
7	M4: App usage monitoring & limits.
8	Real-world testing, threshold tuning for both classifiers, false-positive/negative logging.
9	Optional modules (M5–M7) as time permits.
10	Hardening, performance/battery profiling, final documentation & defense prep.
